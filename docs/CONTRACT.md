# Shared implementation contracts (v2)

Public interface contract for the experimental single-owner implementation. The current supported deployment target is Linux amd64; source availability does not establish every acceptance gate.

These contracts coordinate the host, runtime, UI and deployment implementations. Propose a contract adjustment before editing another subsystem. JSON uses snake_case; all times in HTTP payloads are RFC3339 UTC; scheduling separately stores its IANA timezone. API success is JSON unless streaming or downloading. Errors: `{error:{code,message,retryable,diagnostic_id}}`.

## Layout and identities

- `host/`: Go module `personalbot.local/host`, commands `cmd/personal-bot-gateway`, `cmd/personal-bot-helper`, `cmd/personal-botctl`.
- `runtime/`: Python package `personal_bot`, FastAPI app entry `personal_bot.api:app`; worker entry `python -m personal_bot.worker`.
- `web/`: React/TypeScript/Vite, output `dist/`, relative `/api` requests with credentials.
- `deploy/`: Dockerfile, s6 configuration, systemd and fixed management configuration.
- Container API UID 31001, Worker 31002, browser 31003, executor 31004, shared IPC GID 31000. Host gateway uses separately installed dedicated account; root helper only accepts that account's peer credentials.
- Runtime data paths: `/data/app` (API-only), `/data/files` (API-managed), `/data/browser` (browser-only), `/scratch` (per-run execution); IPC `/run/personal-bot/`.
- Runtime HTTP listens on port 8091, published only on host loopback; private Worker API uses `/run/personal-bot/worker.sock`.
- Host gateway defaults to `127.0.0.1:8090`; static root configured, not embedded private files. Browser viewer exposed only through gateway authentication.

## Compact deployment profile

Linux amd64, systemd/cgroup v2, Docker, AppArmor and kernel Landlock/seccomp are required. The fixed compact runtime uses 1 CPU / 2 GiB / 256 PIDs, 256-MiB scratch and 256-MiB shm counted within runtime memory; the complete project slice is 1.5 CPU / 2432 MiB. Host admission conservatively reserves at least 768 MiB. Source build and heavy backup maintenance need independent capacity planning with the runtime stopped. No host-wide proxy, DNS or TLS weakening is part of installation.

ARM64 needs native syscall and isolation validation before support is advertised. The default HTTPS entry is loopback plus an SSH tunnel; no production host identity or credential is contained in these examples.

## Request identity

Gateway sends `X-Personal-Bot-Assertion: base64url(payload).base64url(ed25519_signature)` with unpadded base64url. Signature covers the ASCII payload segment. Payload keys: `sub` (owner ID), `role` (`owner` or `control`), `method`, `path` (path only), `request_id`, `exp` (Unix seconds), `deployment_epoch`. Default expiry 30s. Public clients cannot supply authoritative internal headers. API verifies signature with PEM Ed25519 public key at `PERSONAL_BOT_GATEWAY_PUBLIC_KEY`, checks method/path/expiry/deployment epoch. Host supplies `PERSONAL_BOT_DEPLOYMENT_EPOCH` and `PERSONAL_BOT_RUNTIME_ID`.

API health `/health/live` returns fixed nonsecret JSON; `/health/ready` verifies initialization without leaking secrets. Control routes require a signed assertion with role=control; owner cannot invoke them.

Runtime-to-host control uses a dedicated host directory `/run/personal-bot-bridge/` mounted at `/run/personal-bot/host/`, with `bridge.sock` inside. `PERSONAL_BOT_HOST_BRIDGE` identifies the container path. Do not bind only the socket inode or expose the helper directory. Reconnect by path after gateway restart. Actual SO_PEERCRED must match the API identity as seen through the configured UID mapping; payload includes current runtime_id and deployment_epoch. Endpoints: `POST /internal/events` accepts `{event_id,kind,payload,runtime_id,deployment_epoch}`; kinds `schedule.upsert`, `schedule.disable`, `model.wait.upsert`, `notification`. ACK only after durable control DB commit: `{accepted:true,event_id}`. Same event ID with changed content is a conflict. Schedule data uses `{schedule_id,revision,enabled,cron,timezone,next_fire_at}`; model wait `{task_id,wait_generation,connection_revision,enabled,resume_at}` with newer disabled tombstones on cancellation; notification `{notification_id,task_id,category}` with generic body only.

The mounted bridge directory itself must survive full gateway stop/start; configure its lifecycle/RuntimeDirectoryPreserve so only bridge.sock is replaced while a runtime exists. SO_PEERCRED enforcement uses actual accepted credentials, not headers.

Worker IPC must validate SO_PEERCRED from actual accepted socket, not an HTTP header. Agent may use a Uvicorn protocol subclass to put actual credentials in ASGI scope. Only UID 31002 (or explicit test UID setting in test process) can use Worker routes. All task operations additionally check runtime_id and attempt_id.

## Host-owned public routes

- `GET /api/auth/status` -> `{initialized,authenticated,owner:{id,username}|null,csrf_token?:string}`.
- `POST /api/auth/setup/enrollment` `{setup_token,username}` -> `{enrollment_id,totp_uri,totp_secret}` before initialization only. `POST /api/auth/setup` `{setup_token,enrollment_id,username,password,totp_code}` -> owner, csrf_token and one-time recovery_codes, setting the owner cookie. Enrollment data is never sent to a third-party QR service.
- `POST /api/auth/login` `{username,password,totp_code?,recovery_code?}` -> owner + csrf_token; cookie Secure/HttpOnly/host-only, CSRF required for authenticated mutation.
- `POST /api/auth/logout`; `GET /api/auth/sessions`; `DELETE /api/auth/sessions/{id}`.
- `GET /api/runtime` -> `{state,phase,runtime_id|null,elapsed_seconds,server_time,idle_since|null,idle_deadline|null,idle_blockers:[],last_removed_at|null,last_removal_reason|null,safety_suspended,suspension_reason|null,error|null,diagnostic_id|null}`; does not wake. A durable safety_suspended flag overrides ensure/recovery/schedule wake until explicitly cleared by local management; user refresh cannot clear it.
- `GET /api/notifications`; `POST /api/notifications/{id}/read`; Web Push registration `/api/push/subscriptions`.
- Active authenticated runtime requests are proxied after ensure-ready. Passive GET requests marked `X-Personal-Bot-Passive: 1`, all task-event subscriptions and automatic viewer reconnects cannot create or keep a runtime alive. Sleeping returns a clear `runtime_sleeping` result/end event and the UI stops automatic retries. Mutations do not accept passive semantics. Gateway does not return accepted until runtime commits. Stable caller request ID forwarded unchanged. Startup timeout returns clear retryable error; no fake task acceptance.
- Planned maintenance UI: `GET /api/backups`, `GET /api/backups/{id}/download`, `PUT /api/settings/backup-recipient` with validated public recipient only, `GET /api/maintenance/status`, `POST /api/diagnostics/export`. These host-owned operations never let callers supply filesystem paths, shell text or an arbitrary archive for root extraction. Restore/upgrade/rollback remain local personal-botctl operations in v0.1. A sleeping runtime is reported as unavailable in live diagnostics rather than silently woken.

## Runtime-owned public routes

- `POST /api/requests` body `{client_request_id,text,mode:'new'|'supplement',task_id?,conversation_id?,file_ids?:string[]}` -> `{accepted:true,request_id,task_id,task_revision,conversation_id}`. Same request ID returns original receipt. For supplement task_id is required. Conversation continuation is defined below; omitting conversation_id retains the existing new-task behavior.
- `GET /api/requests/{id}` -> receipt, or clear not_found.
- `GET /api/tasks` -> `{items:Task[]}`; `GET /api/tasks/{id}` -> Task.
- Task fields include `id,conversation_id,title,status,revision,created_at,updated_at,connection_id|null,model_id|null,summary?,wait_reason?,result?,tool_count,token_count,unresolved_effect_count`. Statuses match design spec; cancellation can coexist with unresolved external effects.
- `GET /api/tasks/{id}/events?after=N`: SSE `id: seq`, event `task_event`, data `{seq,task_id,kind,data,created_at}`; support Last-Event-ID. Also provide ordinary `GET /api/tasks/{id}/history?after=N` -> `{items:TaskEvent[]}` for deterministic UI reload/testing.
- `POST /api/tasks/{id}/commands` `{command_id,expected_revision,action:'pause'|'continue'|'cancel'|'rerun',text?}` -> Task/receipt; revision conflict=409.
- `GET /api/messages?task_id=...` -> `{items:[{id,task_id,role,content,created_at}]}`.
- `GET /api/model-connections` -> `{items:[Connection]}`; `POST` create; `PATCH /{id}` update; no plaintext key in returned object. Fields `id,display_name,provider,region,billing_mode,protocol,base_url,model_id,capabilities,revision,enabled` plus account/credential/billing-entry/quota bindings, per-scope entitlement evidence and provider-overage status. A key does not imply one quota pool. Omitted api_key preserves the secret; empty is invalid; clearing is explicit.
- `POST /api/model-connections/{id}/overage-approval` is an owner-authenticated, explicit temporary purchased-credit approval. Body requires integer `expected_revision,expected_secret_revision`, `kind:"purchased_credits"`, `acknowledge_purchased_credits:true`; optional `expires_in_seconds<=3600,max_tasks<=3,max_tools<=8,max_tokens<=100000,max_active_seconds<=300` may only lower the fixed limits. Only an enabled subscription with actual `enabled/purchased_credits` overage facts qualifies. `DELETE` revokes. Both return the redacted Connection with `overage_approval:{active,can_create_task,kind,reason,expires_at,max_tasks,tasks_used,remaining_tasks,budgets}`. Approval never changes actual overage facts, is live rather than restored from a connection snapshot, binds config/secret revisions and deployment epoch, and cannot authorize schedules/background. Task enrollment is atomic; retries and actual HTTP sends recheck current authorization. Token budgets are application admission accounting, not a provider-bill guarantee.
- `DELETE /api/model-connections/{id}?expected_revision=N` deletes one saved connection and returns `{deleted:true,id,cleared_default_roles:('chat'|'agent')[]}`. The integer revision is required; a stale revision returns `revision_conflict` (409), and a missing connection returns `not_found` (404). Unfinished dependent tasks, dispatched model requests or an active validation lease return `connection_in_use` (409). The same transaction removes this connection's saved key/configuration, temporary overage authorization and matching default pointers, without selecting another default. Credential/profile/endpoint objects still referenced elsewhere remain; task/message/file/usage history and nonsecret versioned configuration remain. Saving an old edit cannot recreate a deleted connection or overwrite a newer revision.
- Model add/edit uses a named native modal with visible initial focus, Escape/cancel and focus restoration; long forms scroll within the viewport. Deletion requires a separate named confirmation and never validates a model. While list/default reads are pending, mutation entries are disabled so an old list cannot overwrite a saved/deleted result. Conflicts retain the confirmation and require a fresh explicit decision; automatic refresh is passive and never retries the deletion.
- `GET /api/model-presets` -> `{items:[{id,name,billing_modes,protocols,base_urls,notes}]}`.
- `POST /api/model-connections/{id}/validate` -> `{checks:{auth,text,stream,tools,vision},errors:[],validated_at}`. A check is `passed|failed|not_tested`. Saving does not invoke a model. Model configuration changes owner-only.
- `POST /api/settings/default-model` `{role:'chat'|'agent',connection_id}`; `GET /api/settings` -> safe settings/default role bindings/budgets only. Agent bindings require complete tool-roundtrip capability and permitted use scope. Capability evidence is invalidated by relevant configuration changes.
- `PATCH /api/settings/task-budgets` changes defaults for future tasks; `PATCH /api/tasks/{id}/budgets` `{command_id,expected_revision,...limits}` changes one task. Neither resets accumulated usage.
- `GET /api/files` -> `{items:File[]}`; upload `POST /api/files` multipart `file`; `GET /api/files/{id}/download`; delete `DELETE /api/files/{id}`; restore `POST /api/files/{id}/restore`. File `{id,name,media_type,size,status,version,task_id?,created_at,deleted_at?}`.
- `GET /api/memories` -> `{items:[{id,content,status,source,revision,created_at}]}`; POST create explicit memory; PATCH edit/confirm; DELETE removes from retrieval and adds per-item source suppression.
- `GET /api/schedules` -> `{items:Schedule[]}`; POST/PATCH/DELETE with revision and outbox. Schedule `{id,title,prompt,cron,timezone,enabled,revision,registration_status,next_fire_at}`.
- `GET /api/approvals?task_id=...` -> `{items:Approval[]}`; `POST /api/approvals/{id}/decision` `{command_id,expected_revision,decision:'approve'|'reject'}`. Approval contains normalized action + website/account/parameters/file versions and task revision.
- `POST /api/tasks/{id}/tool-calls/{call_id}/reconciliation` `{command_id,expected_task_revision,expected_tool_revision,outcome:'confirmed_done'|'confirmed_not_done'|'unresolved',evidence}`. Record owner reconciliation separately from machine verification; never automatically resume a cancelled task.
- `GET /api/browser/status`; `POST /api/browser/control` `{action:'takeover'|'release'|'transfer',device_id,browser_epoch?,expected_task_id?}`. `POST /api/browser/view-sessions` `{device_id,expected_task_id?}` creates a short-lived viewer session and returns its same-origin WS path, view_session_id, runtime_id, browser_epoch and expires_at. The integrated conversation UI supplies expected_task_id; the r19 binding rules are below. Actual noVNC/RFB input is checked by the server per input message against the current owner/device/epoch; read-only is never a client-only flag. Clipboard/file transfer extensions are disabled. No long-lived bearer in WS URLs. Never use screenshots as proof of actual human takeover unless input is really supported.

## r19 persistent conversations and continuation

- A conversation has `id,title,created_at,updated_at` and contains independently revisioned task executions. It is stored by the API in SQLite and survives runtime deletion. The idempotent upgrade gives each pre-existing task its own conversation, using that task's ID as the migrated conversation ID; parent_task_id alone does not merge historical tasks. Existing task/message IDs, checkpoints, audit history and encrypted credentials remain intact. Newly created conversation and task IDs are separate IDs.
- `GET /api/conversations?limit=50&cursor=...` returns `{items:ConversationSummary[],next_cursor:string|null,has_more:boolean}`. A summary contains `id,title,created_at,updated_at,latest_task_id:string|null,latest_task_status:string|null`. Ordering is stable `(created_at DESC,id DESC)`, not updated_at. Limit is 1–100, default 50; no task prompt/result/message bodies are included.
- `GET /api/conversations/{id}?limit=50&before=...` returns the conversation summary fields plus `{tasks:TaskSummary[],next_before:string|null,has_more:boolean}`. The first page selects the latest executions, then returns that page chronologically by `(created_at,id)`; before reads earlier executions. TaskSummary adds conversation_id to the r17 fields and excludes prompt/result/summary bodies. `GET /api/conversations/{id}/messages?limit=50&before=...` returns `{items:Message[],next_before:string|null,has_more:boolean}` across member tasks, with the latest messages first selected and each page returned chronologically by `(created_at,id)`. Message retains task_id so execution provenance is explicit. Both limits are 1–100, default 50. Cursors are opaque and scoped to their list kind and conversation; invalid or cross-conversation cursors return invalid_cursor.
- `POST /api/requests` with mode=new and no conversation_id creates a conversation and execution atomically. With an existing conversation_id, it creates the next execution in that conversation and sets parent_task_id to its latest prior execution. Ordinary continuation rejects any unfinished member task with `conversation_busy` (409). Any dispatched or unknown external effect in that conversation, including on a cancelled earlier execution, blocks a new execution with `reconciliation_required` (409). A supplement with conversation_id must match the supplied task, otherwise `conversation_mismatch` (409). Initial, retried and queried request receipts include the same conversation_id; existing request idempotency remains in effect.
- The existing explicit rerun command is a compatibility exception: it creates a linked execution in the same conversation and may queue it while its parent is unfinished. Only this command can use that exception; normal new-turn requests cannot enable it. Rerun still blocks unresolved external effects and retains its existing connection, subscription authorization and fresh task-credit admission checks. Execution selection and controls must remain available when more than one execution needs attention. Separate scheduled executions create separate conversations.
- A fresh execution receives prior user/assistant messages and successful tool results from earlier executions in that conversation. Historical tool results are explicitly marked as possibly stale, read-only context; they cannot supply a current browser observation, element reference, approval or authorization to replay an external action. The current execution's completed tools remain separate. Another execution's native provider reasoning/opaque protocol state is not replayed into the new execution or a different model; original saved model steps/checkpoints remain intact, and same-execution checkpoint/resume semantics are unchanged. No paid summarization or automatic context pruning is introduced.
- Active files previously explicitly granted in the same conversation can be read by its next execution. Files/grants from other conversations and deleted grants do not transfer. Restoring a deleted file does not restore an old task grant. External-operation approvals never transfer between executions.
- Conversation list/detail/message reads and automatic refreshes use `X-Personal-Bot-Passive: 1`; their service methods do not update activity. They cannot wake or extend a runtime. An explicit owner action to read history may use the existing active request path, while subsequent automatic refreshes remain passive. Legacy task/message APIs, task commands and history/SSE remain available with their existing pagination and sequence semantics.

## r19 conversation browser binding

- Public `GET /api/browser/status` remains the authenticated owner's global browser status. A conversation workspace displays a browser card/panel only when its returned task_id belongs to that conversation; changing the selected conversation does not move or navigate the live browser. A task's browser.status tool is separately scoped by its server-derived conversation_id: another conversation's live browser is returned as inactive with url/task_id cleared, without starting, changing or closing that browser.
- The integrated UI supplies `expected_task_id` for viewer-ticket creation and takeover/release/transfer. It must identify an existing task and match the broker's current task; a changed binding returns `browser_task_changed` (409) instead of attaching to the other execution. Omitting the field remains compatible with existing engineering clients. This check supplements owner, login-session, device and epoch verification; it does not replace them. Every ticket also binds the current task, including the no-task state, and is rejected after that task changes.
- When browser use moves to another task, the broker increments the epoch, clears observation/element references, revokes tickets, closes viewers and stops the old input bridge before the next task can use the page. Within the same conversation, the current page can continue across executions. Across conversations, the broker creates a genuinely new page and closes the previous pages, removing back/forward access to another conversation's page. The owner's shared browser profile/cookies remain persistent; this is not a separate browser profile per conversation. Task/conversation identity is taken from the API's task record, never from model-controlled action data.
- Browser use remains visible as a message-area card that opens a panel inside the conversation. Opening a different conversation closes the old UI panel; a stale browser task binding closes/refuses that viewer. On mobile, the panel has modal focus containment, an explicit return-to-conversation action and an accessible stop-task control. Read-only status/viewer traffic keeps the existing passive rules; an unused viewer ticket still cannot start x11vnc. The r17 30-second last-viewer retirement and runtime's 300-second idle deletion remain unchanged.

## r19 workspace navigation

- The primary workspace is a persistent conversation list, chronological messages and composer, with file/browser cards in their conversation. File previews and the actual noVNC browser open in its work panel. Files/results and settings remain secondary destinations; the browser is no longer an independent main navigation tab. The interface remains Chinese, uses local assets/Lucide icons and makes no model call directly from the browser.
- Settings groups models, memory/preferences, account/devices and notifications. Schedules, backup/diagnostics and task-budget controls are inside collapsed advanced settings; detailed execution diagnostics are folded rather than removed. The account is still the single owner: progressive disclosure does not invent separate ordinary-user/admin roles or change backend permissions.
- Pending external approvals, uncertain-effect reconciliation, task stop/pause/continue controls, model quota/credit authorization and material errors remain actionable in the conversation or their existing settings flow. A smaller default interface must not hide a required owner decision, automatically approve an effect or renew purchased-credit authorization. Historical executions are selectable, including an unfinished earlier execution after an explicit rerun.
- Existing `#tasks`, `#files`, `#settings` and `#memories` links remain reachable secondary views. Old browser/unknown top-level hashes resolve to the conversation workspace; current conversation links use `#chat?conversation=...`, and `#chat?new=1` starts a blank composer. Existing API clients do not need to adopt the new navigation or conversation endpoints immediately. Deployment/visual acceptance is recorded separately in STATUS.md; this contract alone is not release evidence.

## r17 passive read pagination

- Legacy `GET /api/tasks` and `GET /api/messages?task_id=...` retain their existing `{items}` shape, fields and ordering. Pagination is explicit and does not change task revisions or activity timestamps.
- `GET /api/tasks?view=summary&limit=50&cursor=...` returns `{items:TaskSummary[],next_cursor:string|null,has_more:boolean}`. Limit is 1–100, default 50. Summaries are ordered by `(created_at DESC,id DESC)` and contain `id,title,status,revision,created_at,updated_at,execution_mode,parent_task_id,schedule_id,wait_reason,tool_count,token_count,active_seconds,unresolved_effect_count,token_usage_estimated`. `title` is capped at 64 characters and `wait_reason` at 240; prompt/result/summary bodies are neither queried nor returned. Fetch the selected task through the existing detail endpoint.
- `GET /api/messages?task_id=...&view=page&limit=50&before=...` returns `{items:Message[],next_before:string|null,has_more:boolean}`. Limit is 1–100, default 50. The first page contains the latest messages; each page is returned chronologically by `(created_at,id)`, and `next_before` fetches older messages. The cursor is opaque, versioned and scoped to this task and list kind. Invalid or cross-list/task cursors return `invalid_cursor`; callers must not construct cursors or use SQLite rowids.
- History accepts `after` (nonnegative) and optional `limit` (1–1000, default 1000), returning `{items:TaskEvent[],next_after:number,has_more:boolean}`. `next_after` is the last delivered global sequence, or the supplied `after` when empty. Follow pages until `has_more=false`, then subscribe to SSE from the last sequence. Sequences are globally increasing and can have gaps within one task; deduplicate by sequence without requiring adjacent values. Legacy consumers can continue reading `items`.
- Paging, SSE and automatic catch-up remain passive: they neither wake the runtime nor refresh its activity. An unavailable/sleeping runtime ends background retries. No conditional-cache semantics are inferred from task revision.
- The UI loads summaries and fetches a selected task's detail separately. `model.text_delta` changes displayed text only; other events invalidate affected resources through a 250-ms coalescing window. Healthy SSE replaces periodic message polling; a disconnected stream uses paged passive catch-up. Late requests cannot overwrite a newer selection or paging window, and a slow fallback request cannot multiply into concurrent refreshes.

## r17 watched display lifetime

- Browser use starts Chromium, Xvfb and its required proxy without x11vnc. Creating an unused viewer ticket does not start the display service. Only a valid, authenticated viewing WebSocket can start its private x11vnc transport; an invalid viewer cannot consume that service or obtain input permission.
- The last disconnected viewer starts a 30-second grace period. A valid new viewer cancels retirement; otherwise x11vnc stops while Chromium, Xvfb and the page remain available. This grace period is unrelated to the existing runtime's 300-second idle deletion and does not refresh runtime activity.
- Takeover, transfer, release, controller-session revocation and ownership-epoch changes close old viewer connections and the old input bridge before a new viewer can establish a bridge. Server checks remain authoritative for each input message; old device/epoch inputs must not reach a new ownership session. Last-viewer retirement clears held keys with the bridge, without closing the Chromium page.
- Browser status may additionally contain `display_running:boolean`, `viewer_count:number` and `browser_start_seconds:number|null`. `viewer_count` counts established viewer connections rather than unconsumed tickets. These fields and passive status polling are observational; they do not start the browser or extend its lifetime. Existing clients may ignore the new fields.
- Human-control expiry closes the browser according to the existing policy. It does not grant a new five-minute runtime lifetime: deletion depends on actual activity and current blockers and can occur shortly after expiry. No separate 120-second browser idle timer, warm pool or memory-snapshot restoration is introduced.

## r17 content-free performance records

- Each dispatched task-model attempt records a `model.input_measured` task event with `model_call_id`, zero-based `attempt`, `measurement:"compact_json_utf8"`, `raw_messages_utf8_bytes`, `input_utf8_bytes`, `tool_schema_utf8_bytes`, `request_json_utf8_bytes` and `message_count`. A cached completed model step returns without another measurement. Attempts prevented from sending retain their separate not-sent/failure outcome; a measurement alone is not proof of a network send or provider charge.
- Sizes use UTF-8 compact JSON with non-ASCII characters preserved. `raw_messages_utf8_bytes` measures the source message list; `input_utf8_bytes` measures protocol-mapped messages or Responses instructions/input; schema and total request JSON have separate counters. They are byte counts, not token estimates or an HTTP/TLS wire capture. The event contains no prompt/message/schema body, API key or extra content copy. Provider-reported usage remains separate and unknown usage remains explicitly unknown.
- Host emits `container_create` and `runtime_ready` durations with runtime identity and created/adopted/success facts. Runtime emits `api_initialized`, `task_initialized`, `browser_started` and `first_tool_completed` durations with applicable task/runtime IDs. API initialization is measured within its lifespan before serving, rather than from container creation; task initialization includes first lazy graph loading when needed; browser startup covers Chromium/Xvfb/proxy initialization; first-tool time runs from the start of the claimed task and includes preceding work. Stages have different starts and can overlap, so their durations must not be added as a cold-start total.
- Timing records contain IDs, stage names and elapsed seconds only. Failure to write diagnostic output cannot change a successful tool/browser result or trigger an uncertain retry. Measurements add no paid summarization call and do not mutate model input or trim history. Original audit/checkpoints, MiniMax reasoning and Responses opaque items remain intact. Future context pruning requires task-scoped read-only result retrieval and its own protocol/recovery acceptance.

## Runtime control routes

- `POST /internal/quiesce` signed role=control with drain_id and expected intake revision: atomically close intake only if no previously accepted executable work blocks idle recycling, checkpoint/stop children/browser, flush ALL durable control outbox, return `{safe_to_remove,deployment_epoch,runtime_id,drain_id,intake_revision,pending_external_actions,pending_outbox}`. New request at closed intake returns retryable draining error, never accepted. v0.1 drain is one-way once committed: there is no resume-intake operation; requests wait for the next runtime. Old-version control requests cannot change the gate; same-runtime gateway transitions are serialized.
- `POST /internal/dispatch` signed role=control `{event_id,kind,payload}`: create/skip scheduled task or resume appropriate model waiting generation transactionally; idempotent receipt.
- `GET /internal/activity` signed role=control -> `{runtime_id,executable_tasks,human_control,last_activity_at,safe_idle}` used for idle decision. Polling itself does not refresh activity.

## Browser/executor hooks (root agent owns implementations)

Root supplies `personal_bot.sandbox` and `personal_bot.browser` modules; runtime owner should call through these APIs rather than writing a second implementation. Sandbox contract will be finalized with runtime owner before use; network/shell disabled and failing capability tests must fail closed. Browser has separate UID/profile, ownership epochs and authenticated broker; not an arbitrary JS/CDP tool.

## Testing and unknowns

No production key or user data is included. Deterministic mock model tests are not provider evidence. The public source is an experimental release: independent clean installation, native ARM64, the complete provider matrix and full resource/fault/rollback gates remain open. Failed isolation must fail closed. Test probes can mutate isolated acceptance state and must never be run on an owner's production instance without a specific maintenance procedure. See STATUS.md for current evidence boundaries.
